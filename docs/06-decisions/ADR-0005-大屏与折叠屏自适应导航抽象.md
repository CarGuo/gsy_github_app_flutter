# ADR-0005 大屏 / 横屏 / 折叠屏自适应导航抽象

- 状态：已采纳
- 日期：2026-09-01
- 相关：ADR-0001 状态管理收敛策略、ADR-0002 新增功能默认状态方案

## 背景

GSY 长期只在竖屏手机形态下验证，桌面 / 平板 / 折叠屏用户会遇到三个可见现实问题：

1. **首页与详情两栏 layout 只用竖向 `BottomNavigationBar`**：横屏时底部导航压缩正文，视觉极不合理；平板 / 折叠屏时中间大面积留白。
2. **[code_detail_page_web.dart](file:///d:/workspace/project/gsy_github_app_flutter/lib/page/code_detail_page_web.dart) 曾锁 portrait**：进出后没解锁全局 orientation，导致其他页面在横屏下也被强制拉回竖屏。已在 P0 `f361cb9` 修复。
3. **列表项在 ≥600dp 宽度下行长过长**：卡片宽度没有任何上限，1280dp 屏上一行文本贴到两侧边距，可读性差。

问题的**根因不是缺一段响应式代码**，而是缺一个「谁在哪个断点该切换成什么」的抽象层。P0 阶段（`3b6967f` / `e25bc48` / `2613c3c`）先把断点工具和旋转相关的错位修好；P1 阶段（`c97afe0` / `39c25e8`）真正引入两态导航时，就不得不直面一个决策：

> **导航层用什么框架 / 抽象承载？**

## 候选方案

调研当时（2026-09）Flutter 生态自适应导航 / 骨架的三条主路径：

### 方案 A：直接绑 `flutter_adaptive_scaffold`

Google 官方在 2023 年初发布的自适应 Scaffold 组件，出厂即支持 compact / medium / expanded 三档，以及 slotLayout 语义。

**否决原因**：

1. **官方已 discontinued（2025-04）**：仓库 README 明示不再维护，issue 长期无人回复。绑一个已废弃的包做核心导航层，等同预埋"未来必然要重来"的风险。
2. **社区继任者 `adaptive_scaffold_router` 强绑 `go_router`**：GSY 目前用 `Navigator 1.0` + Redux/Provider/Riverpod 混合路由（见 ADR-0001），迁到 `go_router` 是**跨模块重构**，触发 AGENTS.md 的"不做顺手重构"红线。
3. **API 表面积过大**：`AdaptiveScaffold.standardNavigationTypeBuilder` 一个 builder 就吃掉 rail / drawer / bottom / permanent-drawer 四种形态，改一处影响四种断点。GSY 首页容器承担 tab 切换 + drawer + 双击回顶 + Android 返回键回桌面**四种非导航职责**，塞进这个 API 会立刻打乱现有 `_navigationTapClick` / `_navigationDoubleTapClick` / `PopScope` 的调用点。

### 方案 B：`responsive_framework` 类整层缩放

第三方"魔法响应式"库，用一套百分比换算把整棵 widget tree 按屏宽等比缩放。

**否决原因**：

1. **和 Material 3 断点语义冲突**：Material 3 三档语义（compact / medium / expanded）是内容组织策略，不是像素等比。用等比缩放会让 rail 在平板上按比例变大，最终变成"手机放大 3 倍"。
2. **对 platform 感知差**：折叠屏的 hinge / posture 完全无法用宽度百分比表达，`responsive_framework` 没有对应能力。

### 方案 C（本 ADR 采用）：Strategy Delegate + Material 3 原生断点

自建一层**框架无关的导航策略接口** [GSYAdaptiveNavigationDelegate](file:///d:/workspace/project/gsy_github_app_flutter/lib/common/style/gsy_adaptive_shell.dart#L41-L54)，默认实现走 Flutter Framework 原生 [NavigationRail](https://api.flutter.dev/flutter/material/NavigationRail-class.html)；断点直接复用 Material 3 Window Size Classes 定义，由 [GSYResponsiveContext](file:///d:/workspace/project/gsy_github_app_flutter/lib/common/style/gsy_responsive.dart#L38-L62) extension 暴露给业务层。

## 决策

**采用方案 C：Strategy Delegate + Material 3 原生断点**。

### 消费方约束

- **[GSYTabBarWidget](file:///d:/workspace/project/gsy_github_app_flutter/lib/widget/gsy_tabbar_widget.dart) 是唯一直接消费 `GSYAdaptiveNavigation.instance.buildRail` 的地方**；[GSYPullLoadWidget](file:///d:/workspace/project/gsy_github_app_flutter/lib/widget/pull/gsy_pull_load_widget.dart) 与 [GSYPullNewLoadWidget](file:///d:/workspace/project/gsy_github_app_flutter/lib/widget/pull/gsy_pull_new_load_widget.dart) 是唯一直接消费 `GSYAdaptiveNavigation.instance.wrapListChild` 的地方（P2 §1 新增）；[UserHeaderBottom](file:///d:/workspace/project/gsy_github_app_flutter/lib/page/user/widget/user_header.dart#L330-L414) + [base_person_state.dart](file:///d:/workspace/project/gsy_github_app_flutter/lib/page/user/base_person_state.dart#L119-L131) 是唯一直接消费 `GSYAdaptiveNavigation.instance.wrapUserStatsBar` / `userStatsBarHeight` 的地方（P2 §3 新增：一个负责递交 5 个 slot，一个负责把高度让给 SliverPersistentHeader）。所有页面（[home_page.dart](file:///d:/workspace/project/gsy_github_app_flutter/lib/page/home/home_page.dart) 已改，后续二级容器如需引 rail 也按同样入口）**只声明** `List<GSYAdaptiveDestination>` 或使用现成的 pull widget / stats slot 列表，不感知 Material NavigationRail / `ConstrainedBox` / `Row + divider` 具体骨架。未来若个别页面（例如 [trend_page.dart](file:///d:/workspace/project/gsy_github_app_flutter/lib/page/trend/trend_page.dart) 里的 `ListView.builder`）需要接入 `wrapListChild`，走 GSYPullLoadWidget 收口或封装同族 helper，**禁止在页面里再另起一个 `GSYAdaptiveNavigation.instance` 直连点**——策略单例没有物理隔离，靠这条约束守死。
- **默认实现 [MaterialAdaptiveNavigationDelegate](file:///d:/workspace/project/gsy_github_app_flutter/lib/common/style/gsy_adaptive_shell.dart#L173-L327) 是整个项目里唯一 `new NavigationRail(...)` 的地方**。未来若要换 `flutter_adaptive_scaffold` 的社区继任者 / 自研 Cupertino 侧栏 / 折叠屏 dual-pane，只写一个新 delegate 就够。
- **Master-Detail 消费口径（P2 §2 新增）**：所有想在大屏走"detail 挂右列"的 tap 分派**必须**走 [GSYAdaptiveNavigation.instance.openDetail(context, detail)](file:///d:/workspace/project/gsy_github_app_flutter/lib/common/style/gsy_adaptive_shell.dart#L423-L428)，禁止在页面里再写 `if (context.canShowTwoPane) { ... } else { Navigator.push(...) }` 这种"半抽象半手写"分支——两处判定漂移一定会踩"drawer 里关了强制全屏但页面没读到"这种最难查的 bug。当前收口点：[trend_page.dart#L91](file:///d:/workspace/project/gsy_github_app_flutter/lib/page/trend/trend_page.dart#L91)、[navigator_utils.goReposDetail](file:///d:/workspace/project/gsy_github_app_flutter/lib/common/utils/navigator_utils.dart#L104)、[navigator_utils.goIssueDetail](file:///d:/workspace/project/gsy_github_app_flutter/lib/common/utils/navigator_utils.dart#L198)；后续二级导航接入的**唯一姿势**就是把 `Navigator.of(context).push(...)` 换成 `GSYAdaptiveNavigation.instance.openDetail(context, ...)`，返回 Future 语义完全一致。
- **断点判定统一走 [GSYResponsiveContext](file:///d:/workspace/project/gsy_github_app_flutter/lib/common/style/gsy_responsive.dart#L38-L62) extension**：`context.isCompactWindow` / `context.isMediumWindow` / `context.canShowTwoPane` / `context.verticalHinge`。禁止在页面里手写 `MediaQuery.sizeOf(ctx).width < 600`——重复口径就是策略腐化的开端。**注意 `context.canShowTwoPane` 只判"能不能"（尺寸维度），是否"要不要"走双栏由 delegate 的 [canShowTwoPane](file:///d:/workspace/project/gsy_github_app_flutter/lib/common/style/gsy_adaptive_shell.dart#L111-L127) 收口再叠加 `forceFullScreenDetail` 用户偏好**——页面代码只 `openDetail`，不需要感知这个二级判定。

### 替换协议（写给未来）

假设未来要接 `adaptive_scaffold_router` 或任何第三方框架，标准动作只有三步：

```dart
class AdaptiveScaffoldRouterDelegate extends GSYAdaptiveNavigationDelegate {
  @override
  bool shouldUseRail(BuildContext context) => /* 第三方框架的断点判定 */;

  @override
  Widget buildRail({ ... }) => /* 第三方框架的 rail widget */;
}

// 在 lib/app.dart 或 lib/main.dart 里做一次全局注入
GSYAdaptiveNavigation.instance.setDelegate(AdaptiveScaffoldRouterDelegate());
```

**页面代码零改动**。这就是本 ADR 的核心承诺。

## 后果

**优点：**

- 页面代码 **只依赖 GSY 自有的抽象**，不引任何三方 rail / scaffold 包，也不直接引 `NavigationRail`。切库时改动面被压到"新写一个 delegate + 一行 setDelegate"。
- 断点定义**单一来源**：Material 3 三档在 [GSYBreakpoints](file:///d:/workspace/project/gsy_github_app_flutter/lib/common/style/gsy_responsive.dart#L13-L28) 写死一次；所有页面走 [GSYResponsiveContext](file:///d:/workspace/project/gsy_github_app_flutter/lib/common/style/gsy_responsive.dart#L38-L62) 消费。要调断点值只改这一个文件，测试文件 [gsy_responsive_test.dart](file:///d:/workspace/project/gsy_github_app_flutter/test/common/style/gsy_responsive_test.dart) 会立刻捕获回归。
- **契约测试 [gsy_adaptive_shell_test.dart](file:///d:/workspace/project/gsy_github_app_flutter/test/common/style/gsy_adaptive_shell_test.dart) 保护"delegate 可替换" 这条承诺**：`setDelegate` 之后 `shouldUseRail` 与 `buildRail` 都要走新实现；`resetDelegateForTest` 复位不留残余状态。谁改这个抽象层，必须先在这里改测试。

**代价：**

- 需要维护自有抽象，Material 3 官方若后续放出更完备的原生 scaffold，我们要评估是不是把默认 delegate 替换掉（**替换的是 delegate 而不是接口**，成本受控）。
- 折叠屏 posture / hinge 相关的高阶能力（例如 `TwoPane` 类布局）**目前只在 [GSYResponsiveContext.verticalHinge](file:///d:/workspace/project/gsy_github_app_flutter/lib/common/style/gsy_responsive.dart#L52-L62) 暴露了检测能力**，实际的 dual-pane widget 还没实现（推到 P2 / P3 阶段）。ADR 只承诺"能识别"，不承诺"已铺满"。
- 单例 `GSYAdaptiveNavigation.instance` 是**全局状态**——测试之间强制 `resetDelegateForTest` 复位是硬约束，忘了会导致跨用例串扰。已在 [gsy_adaptive_shell_test.dart](file:///d:/workspace/project/gsy_github_app_flutter/test/common/style/gsy_adaptive_shell_test.dart#L14-L17) 的 `tearDown` 里固化。

## 演进

抽象层不是一次性拍板的静态接口，而是随 roadmap wave 逐步扩展。每次扩展必须走"先加 delegate 契约 → 补契约测试 → 只在既定唯一消费点接入"这条流水线，禁止在页面里绕开抽象自己糊。

### wrapListChild（P2 §1，2026-09-02）

**动机**：P1 完成后大屏横屏 rail 已就位，但列表卡片仍会拉到 1200dp+ 宽，可读性差。P2 §1 需要给列表 item 提供一个"compact 原样、medium/expanded 限宽居中"的自适应出口。

**为什么加到 delegate 而不是加到消费方**：如果把 `ConstrainedBox(maxWidth: 720)` 直接写到每个列表页，每次换实现（比如未来 `flutter_adaptive_scaffold` 官方继任者出限宽 API）都要挨个页面改。加到 delegate 后，换实现只需重写这一个方法。

**契约**（见 [GSYAdaptiveNavigationDelegate.wrapListChild](file:///d:/workspace/project/gsy_github_app_flutter/lib/common/style/gsy_adaptive_shell.dart#L66-L69)）：

- compact 下**必须原样返回 child**（`identical(wrapped, child) == true`）；多一层 `Center` 都会让 tap 命中区错位或列表 layout 抽风，契约测试用 `identical` 断言把这条锁死。
- medium / expanded 下应在保证水平居中的前提下把 child 约束到 `GSYBreakpoints.cardMaxWidth`（720dp）以内；具体骨架允许 delegate 覆盖（当前默认实现是 `Align(topCenter) + ConstrainedBox`）。
- 不允许注入任何滚动 / 剪裁行为，只做水平居中 + 限宽。

**唯一接入点**：[GSYPullLoadWidget._getItem](file:///d:/workspace/project/gsy_github_app_flutter/lib/widget/pull/gsy_pull_load_widget.dart#L108-L111) 与 [GSYPullNewLoadWidget](file:///d:/workspace/project/gsy_github_app_flutter/lib/widget/pull/gsy_pull_new_load_widget.dart) 的外部 `itemBuilder` 出口。空态 / progressIndicator 保持不包装（否则 loading 也被顶偏到 720dp 里再居中，视觉上很奇怪）。**未走 GSYPullLoadWidget 的页面（如 [trend_page.dart](file:///d:/workspace/project/gsy_github_app_flutter/lib/page/trend/trend_page.dart) 里的 `ListView.builder`）目前不受抽象层覆盖**，需要显式接入才生效；这条口径在 P2 §2 Master-Detail 时会再收一轮。

**验证**：契约测试 [gsy_adaptive_shell_test.dart](file:///d:/workspace/project/gsy_github_app_flutter/test/common/style/gsy_adaptive_shell_test.dart) 补 4 case，全测 21 通过；真机 [tool/ai/smoke/open_card_width_dual.ps1](file:///d:/workspace/project/gsy_github_app_flutter/tool/ai/smoke/open_card_width_dual.ps1) 双分支（compact ~460dp / expanded ~1440dp）截图证据落 [tool/ai/smoke/p2s1_*.png](file:///d:/workspace/project/gsy_github_app_flutter/tool/ai/smoke)。

### Master-Detail 契约与 Shell 集成（P2 §2，2026-09-02；M1/M2 fixup 同日闭环）

**动机**：P1 的 Rail vs BottomTab 只解决"导航容器要不要横过来"，但没解决"expanded 分档下详情页仍然把 master 整片盖住"这条最刺眼的可读性问题。P2 §2 需要在 shell 层引一层"detail 挂到独立 Navigator"的能力，让 Home 三 tab 的 `goReposDetail` / `goIssueDetail` / trend tap 在大屏走"master + detail 两列"，在小屏和用户明确关双栏时透明退回原来的整屏 push。

**为什么加到 delegate + 一个独立 detailNavigatorKey 而不是抽象成 `GSYTwoPane` widget**：Master-Detail 的本质**不是**"把两块内容并排放"，而是"detail 走一条独立于 master 的 route 栈"——单独包一层 `GSYTwoPane` widget 只是"把 Row 起个名字"，Route 语义（`.push().then()` 语义、系统返回键、`Navigator.of(context)` 找哪个 Navigator）仍然一团糟。把能力挂在 delegate（判定 + 分派）+ shell（挂 `Navigator(key: detailNavigatorKey)`）上更贴 GSY 的既有 layering，也让页面消费点**只需要**从 `Navigator.push` 换成 `openDetail(context, ...)`，不改任何返回值处理。

**契约**（见 [GSYAdaptiveNavigationDelegate](file:///d:/workspace/project/gsy_github_app_flutter/lib/common/style/gsy_adaptive_shell.dart#L111-L166) 4 个方法 + [GSYAdaptiveNavigation](file:///d:/workspace/project/gsy_github_app_flutter/lib/common/style/gsy_adaptive_shell.dart#L371-L384) 单例上的 `detailNavigatorKey` / `popDetailToRoot`）：

- `canShowTwoPane(context)` 语义是 "expanded && !isNarrowHeight && !forceFullScreenDetail" 三项与逻辑，任何一条不满足都必须返回 false。**页面代码禁止再自己判 `context.canShowTwoPane`**，一律走 `openDetail`——两处判定漂移一定会踩"drawer 里关了强制全屏但页面没读到"这种最难查的 bug。
- `openDetail(context, detail, {routeName})` 返回 `Future<T?>`，语义与 `Navigator.of(context).push` 完全一致。双栏时 push 到 `detailNavigatorKey.currentState`，单栏时兜底走根 Navigator——`notify_page` 里 `.then((_) => _forceRefresh())` 依赖 Future 在 detail pop 后 complete，本契约在两条分支上都必须保持这个语义。
- `forceFullScreenDetail` / `setForceFullScreenDetail(bool)` 是**delegate 内部状态**，由 [AppForceFullScreenDetailState](file:///d:/workspace/project/gsy_github_app_flutter/lib/provider/app_state_provider.dart#L48-L64) provider 在 `change()` 时同步镜像过去。这层镜像的存在理由：**delegate 不能反向依赖 Riverpod ref**（要保持可单测、可脱离 provider 树跑），因此走"provider 是权威源 + delegate 是本地缓存"的单向同步模式。
- `detailNavigatorKey` 是**全局单例持有的 GlobalKey**（不是 shell 每次 rebuild new 一个）。理由：detail 栈的生命周期要跨 shell 的 rebuild 存活（否则每次分档抖动都会清空用户在 detail 里的浏览进度）；`resetDelegateForTest()` 里会重建这个 key，避免多测试串栈。
- `popDetailToRoot()` 语义是"把内嵌栈弹到根路由（即 GSYTwoPaneDetailPlaceholder）"，**在 detailNavigatorKey 未挂载时是安全 no-op**——单栏路径调它不会崩、也不会误弹根 Navigator。

**Shell 侧集成**（见 [GSYTabBarWidget](file:///d:/workspace/project/gsy_github_app_flutter/lib/widget/gsy_tabbar_widget.dart#L207-L266)）：

- 只在 `useRail` 分支上叠一层 `Row(Expanded(flex:42, master), VerticalDivider, Expanded(flex:58, Navigator(key: detailNavigatorKey)))`，flex 比对齐 [GSYBreakpoints.masterMaxRatio=0.42](file:///d:/workspace/project/gsy_github_app_flutter/lib/common/style/gsy_responsive.dart)；空态由 [GSYTwoPaneDetailPlaceholder](file:///d:/workspace/project/gsy_github_app_flutter/lib/common/style/gsy_adaptive_shell.dart#L447-L483) 承担，文案走 l10n（`two_pane_detail_empty_title` / `two_pane_detail_empty_hint`）。
- **`GSYTabBarWidget` 必须是 [ConsumerStatefulWidget](file:///d:/workspace/project/gsy_github_app_flutter/lib/widget/gsy_tabbar_widget.dart#L10-L70)**，在 build() 里 `ref.watch(appForceFullScreenDetailStateProvider)`（**M1 fixup 契约，2026-09-02 reviewer 闭环**）：因为 `canShowTwoPane` 内部读的是 delegate 单例的 `_forceFullScreenDetail`，delegate 不通知 Widget rebuild，如果 shell 不 subscribe provider，SwitchListTile 翻转后会出现"值已经镜像到 delegate 但 shell 还没 rebuild"的错位（M1 缺口）。这里的 `ref.watch` **不是为了拿值**（值已经在 `canShowTwoPane` 里被读），只是**订阅变更信号**。
- **`_navigationTapClick` 与 `_navigationPageChanged` 里必须调 [GSYAdaptiveNavigation.instance.popDetailToRoot()](file:///d:/workspace/project/gsy_github_app_flutter/lib/widget/gsy_tabbar_widget.dart#L123-L163)**（**M2 fixup 契约，2026-09-02 reviewer 闭环**）：切 master tab 时右列必须回 placeholder，否则会出现"Trend 打开仓库 A → 切 Dynamic tab，右列仍显示 A 仓库详情"的跨 tab 语义错位。`popDetailToRoot` 在单栏是 no-op，因此 compact / medium 路径不受影响。同样在 [dispose](file:///d:/workspace/project/gsy_github_app_flutter/lib/widget/gsy_tabbar_widget.dart#L88-L98) 与 [didChangeMetrics](file:///d:/workspace/project/gsy_github_app_flutter/lib/widget/gsy_tabbar_widget.dart#L99-L121)（分档回退）里也要清栈，防止分档抖动时游离 route 复活。

**唯一接入点**：所有想在大屏走"detail 挂右列"的 tap 分派必须走 `GSYAdaptiveNavigation.instance.openDetail`。当前收口点 3 处：[trend_page.dart#L91](file:///d:/workspace/project/gsy_github_app_flutter/lib/page/trend/trend_page.dart#L91)（保留 OpenContainer 作单栏 fallback）、[navigator_utils.goReposDetail](file:///d:/workspace/project/gsy_github_app_flutter/lib/common/utils/navigator_utils.dart#L104)、[navigator_utils.goIssueDetail](file:///d:/workspace/project/gsy_github_app_flutter/lib/common/utils/navigator_utils.dart#L198)。后续二级导航接入姿势就是把 `Navigator.of(context).push(...)` 换成 `openDetail(context, ...)`，Future 语义完全一致。

**验证**：契约测试 [gsy_adaptive_shell_test.dart](file:///d:/workspace/project/gsy_github_app_flutter/test/common/style/gsy_adaptive_shell_test.dart#L442-L816) 覆盖 9 case（`canShowTwoPane` 三分档 + `setForceFullScreenDetail` 立即生效 + `openDetail` 双栏走 detailNavigatorKey / forceFull 走根 Navigator + `popDetailToRoot` 清栈与安全 no-op + `resetDelegateForTest` 换新 key + M1 shell 翻转 provider 即时 rebuild + M2 切 tab pop detail 到根），`fvm flutter test test/common/style/gsy_adaptive_shell_test.dart` 26 case 全绿；`fvm dart analyze lib/widget/gsy_tabbar_widget.dart test/common/style/gsy_adaptive_shell_test.dart` 无新增 issue。真机证据 fixture（CarSmallGuo × Xiaomi Pad，rotation=1 + density=240 撑到 expanded 分档）：[m1m2_20260902_1604/06_back_to_two_pane.png](file:///d:/workspace/project/gsy_github_app_flutter/tool/ai/smoke/evidence/m1m2_20260902_1604/06_back_to_two_pane.png)（drawer 关闭强制全屏后立即回双栏 + placeholder）/ [m1m2_20260902_1604/15_final_single_pane_confirmed.png](file:///d:/workspace/project/gsy_github_app_flutter/tool/ai/smoke/evidence/m1m2_20260902_1604/15_final_single_pane_confirmed.png)（再翻开强制全屏 ON 后动态列表卡片占满整个 x 轴、placeholder 从 UI 树消失、dump 断言 `placeholder marker count == 0`），M1 双向可逆性得到视觉+dump 双重验证。**已知真机缺口显式登记**：（1）M2 修复的真机端到端脚本（"detail 里 push 页面 → tap rail 切 tab → 观察 detail 回 placeholder"）受"MIUI + wm density 240 后动态卡片 InkWell hit-test 不稳"阻塞，M2 契约由 widget test `M2: 切 master tab（rail 选中项变化）时把 detail 栈 pop 到根` 单测承担；（2）Discussion 详情 / Compare / Search 结果这些二级导航容器仍走单栏，纳入 P2 §2 后续迭代（roadmap §4.1）；（3）折叠屏 hinge 感知未消费，等 P3。

### wrapUserStatsBar / userStatsBarHeight（P2 §3，2026-09-02）

**动机**：P1 完成后 medium 断点下 rail 96dp + 内容区被压到 ~630dp 左右，MyPage 顶部 5 列 stats 均分后每列 ~130dp，`40000+` 这种长数字命中 [minText fallback](file:///d:/workspace/project/gsy_github_app_flutter/lib/page/user/widget/user_header.dart#L302-L308) 一路缩到 8sp，可读性坍塌。P1 §"已知缺口"里显式挂账的"MyPage 5 列在 720dp 横屏溢出"就是这条。P2 §3 需要一个"知道自己在哪一档、自己决定单行还是折栏"的排布出口。

**为什么加到 delegate 而不是加到 UserHeaderBottom**：把"medium 折 3+2、其它单行"的分支塞进 [UserHeaderBottom.build](file:///d:/workspace/project/gsy_github_app_flutter/lib/page/user/widget/user_header.dart#L330-L414) 意味着"排布决策"和"数据装配"混在一起——未来任何 delegate 想改口径（例如 dual-pane 时改 5 列一行、竖折叠屏改 2+2+1），都要回到 UserHeaderBottom 重写一遍分支，等同于把抽象层的"框架无关"承诺漏成筛子。

**契约**（见 [GSYAdaptiveNavigationDelegate.wrapUserStatsBar](file:///d:/workspace/project/gsy_github_app_flutter/lib/common/style/gsy_adaptive_shell.dart#L86-L89) / [userStatsBarHeight](file:///d:/workspace/project/gsy_github_app_flutter/lib/common/style/gsy_adaptive_shell.dart#L99)）：

- `items.length` **必须**为 5，顺序对齐 UserHeaderBottom 递交的 slot（repos / fans / focus / star / honor）；短或长视为 caller bug，delegate 可 `assert`。
- compact / expanded：单行 5 列 + 4 条竖分隔，返回 Widget 与 `userStatsBarHeight` 高度 70 对齐（沿用 [base_person_state.dart](file:///d:/workspace/project/gsy_github_app_flutter/lib/page/user/base_person_state.dart#L119-L131) 原 `bottomSize = 70`）。
- medium：折成 3 + 2 双行，与 `userStatsBarHeight` 高度 130 对齐。行内分隔沿用同款 divider，颜色 / 尺寸由 delegate 内敛，页面完全不感知。
- **3+2 顺序有 semantic**：上排必须是前 3 个 slot（repos / fans / focus），下排必须是后 2 个 slot（star / honor）。delegate 若切成 2+2+1 等其它折栏形态，仍需保持 items 顺序不倒转，防止第三方 delegate 悄悄换 semantic 让 caller 递交的 slot 语义漂移。
- **消费方必须提供有界高度约束**：外层给 `SliverPersistentHeader` 固定 `maxHeight` / `minHeight`，或显式 `SizedBox(height: userStatsBarHeight(ctx))`。medium 双行实现依赖 `Column + Expanded` 摊分等高两行，若在无界高度上下文（如未受限的 `SingleChildScrollView`）里调用，会抛 "RenderFlex children have non-zero flex but incoming height constraints are unbounded"。当前唯一 consumer `base_person_state.dart` 走的是 `SliverPersistentHeader`，兜底 OK；未来新增消费点必须显式复核这一前提。
- **高度必须与排布同源**：任何 delegate 改了排布骨架（例如切成 2+2+1），必须同步在 `userStatsBarHeight` 里改高度值，否则 SliverPersistentHeader 会截掉下半截或空出黑边。这条口径在测试文件的"高度断言"里锁死。
- 只做水平/垂直排布，不注入滚动 / 剪裁 / 主题色覆盖。

**唯一接入点**：[UserHeaderBottom.build](file:///d:/workspace/project/gsy_github_app_flutter/lib/page/user/widget/user_header.dart#L330-L414) 递交 5 个 slot；[base_person_state.dart](file:///d:/workspace/project/gsy_github_app_flutter/lib/page/user/base_person_state.dart#L119-L131) 用 `userStatsBarHeight(context)` 决定 SliverPersistentHeader 高度。**禁止**其它页面另起 `GSYAdaptiveNavigation.instance.wrapUserStatsBar` 直连点——本方法的契约是"专为 5 列 stats 条设计的排布模板"，不是通用 flex 布局工具。

**验证**：契约测试 [gsy_adaptive_shell_test.dart](file:///d:/workspace/project/gsy_github_app_flutter/test/common/style/gsy_adaptive_shell_test.dart) 补 6 case（compact / medium / expanded 三档 layout + 高度断言 + items!=5 assert + setDelegate 后走 sentinel），全测通过；真机 [tool/ai/smoke/open_my_page_stats.ps1](file:///d:/workspace/project/gsy_github_app_flutter/tool/ai/smoke/open_my_page_stats.ps1) 三分档冒烟截图证据落 [tool/ai/smoke/evidence/my_page_stats_*/](file:///d:/workspace/project/gsy_github_app_flutter/tool/ai/smoke/evidence)。**已知真机缺口显式登记**：expanded 分档（wm density 240）真机无法稳定 tap 到 "我的" tab（activity rebuild 让 selectedIndex 归零，rail 项物理坐标随 density 变化不稳），因此 expanded 单行契约由单测 `expanded 窗口 → 单行 5 列 + 高度 70` 保证，真机只留"UI 不崩溃"证据（`p2s3_expanded_no_crash.png`）；后续要补真机 expanded stats 单行截图，前置依赖是把 GSYTabBarWidget selectedIndex 持久化到 provider 层——不在 §3 范围。

## 边界与不做的事

- **本 ADR 起点覆盖 shell 层「Rail vs BottomTab」的切换（P1）；列表卡片限宽 `wrapListChild` 通过 §"演进"章节纳入 P2 §1**。Detail 页面 Master-Detail、折叠屏双栏、hinge 布局都**不在本轮范围**，见 roadmap 大屏适配路线图 P2 §2-§3 / P3。
- **不改路由**。GSY 目前的 `Navigator 1.0` 与 Redux/Provider/Riverpod 混合路由是 ADR-0001 拍板的教学负担；本 ADR 不做"顺手迁到 go_router"这类跨模块重构。
- **不做整层缩放**。响应式的目的是重组内容，不是拉伸像素。
- **不做手机横屏的两栏 Master-Detail**：手机横屏高度 <500dp，塞两栏不如内容优先。[GSYResponsiveContext.canShowTwoPane](file:///d:/workspace/project/gsy_github_app_flutter/lib/common/style/gsy_responsive.dart#L49-L50) 已把这条口径写死。

## 教训

1. **"业内框架先看维护状态"**：`flutter_adaptive_scaffold` 官方级别 + 名字合适，但 2025-04 就废弃了。ADR 决策前必须先看仓库 last commit / issues / PR merge rate，不能只看 API 好不好用。
2. **抽象层的存在是为「未来能换」**：不是为了"现在优雅"。Delegate 模式看着比"直接 new NavigationRail"多一层，但换实现时才知道这层的价值。**用一次抽象换一次自由。**
3. **单例可替换 + 单测强制复位**：任何全局单例都必须暴露一个 `resetXxxForTest`，且 `tearDown` 里必须调。全局单例是 Strategy 模式的实用形态，但也是"跨用例串扰"最容易踩的坑。
4. **命名要反映契约**：`buildRail` 而不是 `buildNavigationRail`——前者是"侧边导航栏"这个概念，后者绑死 Material 类型。命名一步走错，抽象就漏。
5. **文档要和代码同批交付**：本 ADR 与 [gsy_adaptive_shell.dart](file:///d:/workspace/project/gsy_github_app_flutter/lib/common/style/gsy_adaptive_shell.dart) 同一批提交，不能等实施完两周再补。ADR 落后于代码就是"追认现状"，失去决策记录的意义。
